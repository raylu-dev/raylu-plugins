# Sector Mapping

Turn "help me analyze [sector]" into a subsector table the firm can act on: how dense each subsector is, who the notable companies are, how many the firm already tracks in its CRM, how many it has emailed or met recently, and where to focus. The shape follows the Raylu sector taxonomy deliverable: sector, then subsectors, vertical or horizontal, each with its counts.

## When to use

- The user names a sector, vertical, or theme and wants structure, sizing, or coverage.
- Not for finding companies in one narrow niche. That is a market map on its own.

## Flow

Ask one question per message. Skip what the user already said.

1. **Which sector, exactly?** "Give me the sector in a sentence: what is in, what is out." Then, only if unclear: vertical (an industry) or horizontal (a function sold across industries); geography; company size band. Do not ask about goals or thesis.
   Then one more question, before any tool call so the answer is known when the numbers land: "Deliver as tables here in chat, or as a PDF report? Both are available; the PDF is the format we use for sector taxonomies." Skip it when the user already named a format. When the environment has no way to write a PDF, offer chat only and say why.
2. **Find the map.** Call `search_lists_and_maps(search: <distinctive word>)`, twice if the sector has two obvious words; it labels each match List, CRM list, or Market map, and only market maps carry subcategories. Read the description of at most three candidates with `get_list_or_map`; it also prints every column name, so do not call it for maps already ruled out by their title. Three outcomes:
   - One map's description covers the sector: use it, even if it is broader; the user's geography and size band are applied to its rows in step 4. Say so.
   - Several maps each cover a slice: name them with counts and ask which to use. Combine only if the user asks; when combining, dedupe by domain and keep the subcategory from the map that has the company first.
   - None: say the analysis needs a market map, that building one takes 30 to 60 minutes, and offer to start it. On a yes, draft the taxonomy first (step 4's method, without a map to reconcile against), show it, then drive the builder. The builder's steps are fixed: (a) `start_market_map`, then `update_market_map` with a short, clean `category` name (the sector, no notes); the builder writes its own description, in-scope, and out-of-scope from that name, so pass `description`, `inScope`, and `outOfScope` overrides taken from the user's step-1 sentence; (b) it proposes subcategories: select the ones that match your draft and pass your missing ones as extra names, up to 20 in total; (c) regions are a fixed list, so pick the region and put country and size into `firmographics` as free text, omitting size when the user said any size; (d) it may suggest seed companies with garbled names: pick by domain and clean the names, or skip; (e) confirm. Where the user's definition already settles a builder question, answer it without asking the user again; surface only the subcategory list and the final summary. The builder may rename, drop, or merge the subcategories you passed and add one of its own, even with the overrides; on return, reconcile with step 4's rules, using the map's names as the row labels with your agreed name in brackets where they differ, and skip the "Use this breakdown?" question since the taxonomy was agreed before the build: deliver the reconciliation and the table in one message. Tell the user the taxonomy is in this chat, that they should come back in 30 to 60 minutes, and that on return step 3's single status check decides: finished, proceed; still running, wait, since the builder adds companies first and assigns subcategories late, so a partial map reads as mostly "Other". If the user asks for what exists now anyway, pull it and label every number preliminary, with the "Other" count called out as classification pending. Stop there. Do not fake numbers in the meantime.
3. **Pull the map.** `get_list_or_map_rows(map: query, columns: ["name","website","subcategory","country","headcount","revenue","isInCRM","crmAccountId","hasOutreachCampaign","score","dateOfLastTouch","visitOrMeetingHad","lastVisitOrMeetingDate","associateAssigned"])`. Pages hold up to 500 rows: while the count line reads "page X of Y" with X below Y, ask for the next `page`, and read every page before counting. If the reply says the map is still building, say so and treat the pull as preliminary (step 2's return rules). Use `website` for the domain; `primaryDomain` is blank. If the map lacks the last four columns (the `get_list_or_map` column list shows which exist), drop them, and on a project with no CRM integration drop `isInCRM` and `crmAccountId` too. Aggregate the rows with a short script rather than by hand. For the run date on the summary line, call `get_run_status(feature: "market_map", query)` once after the pull; its Finished time is the run date, or Started if still running. Then apply the user's geography and size band to the rows, report how many fell outside, and list rows with no country separately rather than counting them on either side.
4. **Reconcile the taxonomy.** Draft 10 to 20 subsectors for the sector, short noun phrases, vertical or horizontal, the way the Raylu taxonomy does ("P&C Core Systems", "Claims Management & Adjudication"). If the user has their own taxonomy, use theirs. Then read the map's `subcategory` values, normalising case, folding obvious spelling variants of the same name (with and without a suffix) and saying which you folded, and treating "None", "none", blank, and "Other" as one "unassigned" bucket. Finished maps commonly leave a large unassigned bucket; when it holds more than 15 percent of in-scope rows, say every subsector count is a floor, and promote the classification enrichment column from an offer to the first recommendation. Keep the map's names in every table so counts match the app. Note where your draft would split a map bucket, and which draft subsectors have no map rows. Show it and ask "Use this breakdown?"
5. **Aggregate per subsector**, from the rows only: company count; headcount total with "n known"; revenue total with "n known"; in CRM; with a Raylu outreach campaign; met in the last 12 months from `lastVisitOrMeetingDate`; last touch inside 12 months from `dateOfLastTouch`; top five by revenue then headcount, with score. A score of 0 means unscored or disqualified, never low; the map column cannot tell the two apart, so write "0 (unscored or disqualified)", exclude it from "high score" logic, and use 40 or above as "high", stated once. Revenue values under $100,000 are usually data artefacts; count them as unknown.
6. **Emails, from the CRM.** Skip this step when the project has no `crm_search` tool; say so once. Otherwise, the map has no email count, so for the in-CRM rows call `crm_search` in batches, matching on `crmAccountId` (fall back to Website domain only for rows without one), with the question: "For salesforce_account rows whose Id is one of [ids]: per account give Id, and the count of salesforce_task rows linked by WhatId or AccountId with Type starting with 'Email' and ActivityDate in the last 12 months." Keep each question under 950 characters, about 40 IDs. Say how many batches before starting; above 10, ask whether to run all or only the subsectors the user cares about. Save each result to a file; the tool echoes its SQL and rows. Roll up: accounts emailed in 12 months, and accounts with no touch, which means no email, no meeting, and a last-touch date older than 12 months or blank.
7. **External market size, if a web search tool is available.** Run two or three searches at the sector level only: "[sector] market size 2025", "[sector] software market size North America", and one with the sector's broader common name ("veterinary software" for veterinary practice software), since narrower jargon returns press-release aggregators with no figures. Keep a figure only when the result names a year, a scope, a dollar amount, and a source you can link; drop anything you cannot attribute. Published reports rarely match the user's definition exactly, so sort what you keep into at most two classes and label each: the closest published category (often narrower, such as practice management only) and the whole sector (often broader). A North America figure passes for a US and Canada sector; say so. Prefer the latest year within two years of today and state the year on each figure rather than assuming 2025. Report each class as a low-to-high range with the number of reports and a link per figure; when one report sits far outside the others, name it so the reader can discount it. Flag and exclude figures for a market that includes services or hardware when the user's sector is software. Never search per subsector and never allocate a sector figure across subsectors; published reports stop above that level, and an allocation would be a guess. If no search tool exists, skip this step and say so in one clause.
8. **Deliver** with the output contract, in the format chosen at step 1. Chat: the contract as written. PDF: build it to the PDF layout below with whatever document tool the environment has, send the file, and put items 1, 6, and 7 of the contract in chat as well so the recommendation is readable without opening the file. The chat tables can always be added afterwards on request, and the PDF can be produced later from the same rows if the user chose chat first; say so once.
9. **Recommend.** One short paragraph per suggested focus, each citing numbers from the table: a dense subsector with low coverage, a covered subsector gone quiet, a subsector with high scores and no outreach. Without a CRM only the third pattern is available; say so. No claims about the market from outside the table.
10. **Offer, do not do:** tag a subsector's uncovered companies so they show in the app's tag filters (`add_company_tags(map: <map>, companies: <up to 50 domains per call>, tags: ["<Sector> - <Subsector> - uncovered"])`; tags belong to the company and sync to a connected CRM, so say that before tagging); save them as a list instead (`create_list`, then `add_companies_to_list_or_map`); generate outreach for a chosen set; add an AI enrichment column to the map for a question the table cannot answer (for example "does the company sell to hospitals or to practices"), which runs in the background; rerun the map with the geography or size band built in.

## Output contract

1. One line: sector, map used, in-scope rows of rows read, date the map last ran, and how many in-CRM rows the email pass reached (or "no CRM integration").
2. External estimates, when step 7 ran, one sentence per class: "Third-party market size, [category]: $X to $Y ([year], [scope]), N reports" with a link per figure, then "the table below is company density from Raylu data, not a market size". Omit the block when no figure passed the checks, and say so.
3. The taxonomy: subsectors grouped vertical or horizontal, each with its company count; draft subsectors with no map rows listed after; the unassigned bucket last.
4. The main table, one row per subsector, sorted by company count: Subsector · Companies · Headcount (total, n known) · Revenue (total, n known) · In CRM · Emailed 12m · Met 12m · No touch 12m · Raylu outreach · Top companies (up to five). On a project with no CRM integration drop the In CRM, Emailed, Met, and No touch columns rather than showing zeros.
5. Per subsector detail (top companies with headcount, revenue, in CRM, last touch, associate) only for subsectors named in the recommendations, or when the table has under six rows.
6. Coverage line: rows read versus map count, rows outside the geography or size band, rows unassigned, in-CRM rows the email pass did not reach. On a still-running map, say the unassigned count reflects classification not yet done.
7. The recommendation paragraphs.
8. The offers.

Every number in the tables comes from the map rows or a CRM query result. Market size in the tables is company count, headcount, and known revenue; never call it TAM, and say once that no dollar TAM figure exists in Raylu's data. Dollar figures appear only on the external-estimates line, always as a cited range. Conglomerates on a map (a Workday on a legal map) will dominate revenue totals; say so when it happens. Never rank a subsector on outside knowledge.

## PDF layout

Follow the Raylu sector taxonomy deliverable: one sector per document, plain, mostly tables, no charts that need interpretation. Never name another customer, in the question, the file, or the chat; the layout is Raylu's, not any fund's.

1. **Cover.** Sector name, the user's one-sentence definition, geography and size band, map used and its run date, firm name, date. One line: numbers are company density from Raylu data, not a market size.
2. **Taxonomy page.** Subsectors in two groups, Vertical and Horizontal, each row: subsector, company count, coverage tier. Tiers come from the firm's own coverage: Tier 1 when at least half the in-scope companies are in the CRM, Tier 2 when at least a fifth, Tier 3 below that, "n/a" on a project with no CRM. State the tier rule in a footnote. Draft subsectors with no map rows sit under "Not yet on the map"; the unassigned bucket is the last row with its count.
3. **External estimates**, when step 7 ran: the two labelled classes, ranges, years, report counts, and a source list with links in a footnote.
4. **Main table**, the same columns as the chat contract, landscape if needed, sorted by company count.
5. **Subsector detail pages**, one per subsector named in the recommendations (all of them when the table has under six rows): top companies with headcount, revenue, in CRM, last touch, associate.
6. **Coverage and recommendations**: the coverage line, then the recommendation paragraphs, each citing the table.

Every figure in the PDF is the same figure as the table it came from; never restate a number from memory when writing the file. Name the file "[Sector] sector map [YYYY-MM-DD].pdf".

## Projects with and without a CRM

| Project | What changes |
|---|---|
| No CRM integration | Maps lack the Salesforce columns and `crm_search` does not exist; `isInCRM` still exists but reads "No" on every row, so it is not a finding. Say so and deliver density, top companies, score, and Raylu outreach only |
| CRM integration (Salesforce) | Maps carry `isInCRM`, `crmAccountId`, and the integration columns `dateOfLastTouch`, `visitOrMeetingHad`, `lastVisitOrMeetingDate`, `associateAssigned`; `crm_search` reads the CRM mirror (accounts with a last-touch date, tasks typed by activity such as emails and notes, events such as calls and visits). Match CRM queries on `crmAccountId`; domain matching loses a few accounts per batch. `crm_search` allows 30 questions per 5 minutes |

## Common mistakes

- Asking about the user's thesis or check size. Not this skill's job.
- Building the PDF without asking, or asking about the format after the analysis is done. The format question is step 1, before the first tool call.
- Drafting the taxonomy before pulling the rows when a map exists, so it cannot be reconciled with the map's subcategories. (In the no-map path the draft comes first by design and is reconciled on return.)
- Calling company counts "TAM", or spreading a third-party sector figure across subsectors.
- Treating blank revenue or headcount as zero, or a score of 0 as a low score. Zero is unscored or disqualified; say both.
- Reading every candidate map's description. Three at most; titles rule the rest out.
- Asking for `primaryDomain`. It is blank; use `website`.
- Aggregating subcategories without normalising case, which creates phantom rows.
- Sending a crm_search question over 950 characters, or letting the join wording drift between batches.
- Recommending a focus that the table does not support.
